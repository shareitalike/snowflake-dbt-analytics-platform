# Interview Notes: Real-Time vs. Near Real-Time (Micro-Batch)

## 1. "Is your architecture Real-Time or Batch?"
**Answer:** My architecture is **Near Real-Time (NRT)**, which is also known as **Micro-Batch Processing**. 

* **The Ingestion:** Snowpipe automatically ingests JSON payloads from cloud storage as soon as they arrive (typically within 1-2 minutes).
* **The Transformation:** Our Snowflake Task DAG is scheduled to run every 15 minutes (`SCHEDULE = '15 MINUTE'`).
* **The Result:** The overall End-to-End latency (from the source system generating the event to it appearing in the Silver/Gold layer) is roughly **15 to 20 minutes**. 

---

## 2. "Why didn't you build a truly Real-Time pipeline (e.g., using Apache Flink or Kafka Streams)?"
**Answer:** This was a deliberate architectural decision based on cost-to-value ratio. 

True "Real-Time" pipelines (where latency is measured in milliseconds) are incredibly expensive and complex to build and maintain. They require dedicated stream processing engines (like Flink or Spark Structured Streaming) running 24/7. 
Real-time is only necessary for *operational* use cases, such as blocking a fraudulent credit card transaction at the checkout screen, or self-driving car telemetry.

Our architecture serves **Analytical** use cases (BI Dashboards, Machine Learning models, and Financial Reporting). For a CEO looking at a Tableau dashboard to track daily sales, data that is 15 minutes old is highly actionable. Achieving a 15-minute SLA natively within Snowflake (using Streams & Tasks) gave the business 99% of the value at 10% of the cost and engineering complexity.

---

## 3. "What if the business suddenly demands 1-minute data freshness? How would your architecture adapt?"
**Answer:** Because the architecture is completely modular, we can adapt without rewriting the business logic:

1. **The Expensive Way:** We could simply change the root Task definition to `SCHEDULE = '1 MINUTE'`. However, this would keep the Virtual Warehouse spinning 24/7, resulting in massive compute costs.
2. **The Dynamic Tables Trade-Off:** For the Silver-to-Gold layer, the easiest way to get 1-minute latency is to convert the target tables into **Dynamic Tables** with a `TARGET_LAG = '1 MINUTE'`. However, this comes with a massive caveat: Dynamic Tables do not support complex procedural logic (like our Ghost Dimension inference or multi-table metadata updates). 
3. **The High-Frequency Task Trade-off:** If our logic is too complex for Dynamic Tables, we would have to keep our Stored Procedures and change the Root Task to `SCHEDULE = '1 MINUTE'`. To avoid bankrupting the company with 24/7 warehouse costs, we would have to migrate the tasks to **Serverless Tasks**. This shifts the compute management to Snowflake, ensuring we only pay for the exact seconds the 1-minute task is running, rather than keeping a dedicated warehouse spinning all day.
4. **The Streaming Ingestion Way:** For the Bronze layer, we would replace standard Snowpipe with the **Snowpipe Streaming API**. This allows an upstream Kafka connector to write rows directly into Snowflake memory with sub-second latency.

## 4. "How do you handle the 'Kafka Consumer Lag' issue in a micro-batch architecture?"
**Answer:** In a micro-batch architecture, you occasionally experience "Late Arriving Data" (e.g., the source system goes offline and pushes 3 days of data all at once when it recovers). 

Because we process data in 15-minute intervals, we cannot blindly assume that every record in the micro-batch happened exactly 15 minutes ago. This is why our `MERGE` statements explicitly enforce **State Progression**:
`WHEN MATCHED AND src.source_updated_at > tgt.source_updated_at`

By validating the timestamp generated by the *Source System* (rather than the time the data arrived in Snowflake), our micro-batch pipeline is completely immune to out-of-order or late-arriving messages.
